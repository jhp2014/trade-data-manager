# trade-lab 검증 루프

구현이 **끝난 뒤** 돈다. 편집 도중에 돌리지 않는다 — 반쯤 만든 코드를 리뷰하면 미완성을 버그로 보고하고, 그걸 고치다 설계가 흔들린다.

원칙:
- **횟수가 아니라 수렴이 정지 조건이다.** 고칠 게 없으면 1회로 끝낸다. 상한은 안전망이다.
- **2회차는 재리뷰가 아니라 재확인이다.** 수정분 + 1회차 발견사항만 본다.
- **실패는 실패로 보고한다.** PASS 위장·"아마 될 겁니다" 금지.

## 상한

```
reviewer : 1패스 + 재확인 1회      (고칠 것 0이면 재확인 생략)
verifier : 1패스 + 재검증 2회      (FAIL 0이면 즉시 종료, 재검증은 실패 스텝만)
```

## 1. 병렬 1패스 — 한 메시지에서 동시에 띄운다

```
├─ Bash(run_in_background): pnpm --filter @trade-data-manager/lab type-check && pnpm --filter @trade-data-manager/lab test     수 초
├─ lab-reviewer                                              변경 diff 를 넘긴다
├─ lab-verifier #1  주소 http://v1.localhost:3210             시나리오 묶음 1
└─ lab-verifier #2  주소 http://v2.localhost:3210             시나리오 묶음 2 (필요할 때만)
```

- **테스트가 빨간불이면** 리뷰·실측 결과는 받아 두되, 먼저 테스트부터 고친다. 컴파일이 깨진 상태의 실측 FAIL 은 무효로 보고 다시 돌린다.
- **화면에 안 보이는 변경**(타입·순수 로직·문서만)이면 verifier 를 띄우지 않는다.
- verifier 는 사용자 승인 없이 띄운다(사용자 합의 — 병렬 실측). 단 시나리오는 아래 규칙대로 좁힌다.

### lab-reviewer 에 넘길 것

- `git diff`(+ `git diff --cached`), 새 파일은 전체 내용
- 이 변경이 하려는 일 한두 줄
- diff 가 수천 줄이면 본론 파일로 좁히고 나머지는 "기계적 변경"이라고 적는다

### lab-verifier 시나리오는 코드로 못 덮는 것만

스텝마다 묻는다: **"vitest 로 덮이나?"** 덮이면 뺀다. 남길 자격은 셋뿐이다:
1. 실제 브라우저·서드파티가 개입하는 것 — dockview 배치 복원, 크기 측정, 캔버스 실제 그림, lightweight-charts 수명
2. 손짓 — 휠·드래그·수식키처럼 합성 이벤트로는 같은 경로가 안 도는 입력
3. 처음 생긴 화면 상태의 콘솔 침묵 — 런타임 에러 유무는 코드 읽기로 못 본다

**verifier 하나당 스텝 2~3개.** 더 길면 덮이는 걸 안 뺐거나, verifier 를 하나 더 띄워 나눌 때다.

프롬프트에 반드시 넣는다:
- **주소**(verifier 마다 다른 `vN.localhost:3210`) — localStorage 가 분리돼 서로 안 섞인다. dev server 이름은 `lab-dev`
- **시나리오**와 **선행조건**: 고정 실측 대상을 쓴다 — 종목·날짜는 데이터가 확실히 있는 것으로(예: `402340`·`009150` @ `2026-07-31`). 차트·테마·뉴스는 tdm 개발 api(:3011, `api-dev`)가 떠 있어야 한다
- **기하 질문은 "숫자를 달라"로** — "겹치나?"가 아니라 "두 요소의 세로 겹침 px 를 재서 보고하라"

## 2. 발견사항 분류 — 그대로 다 고치지 않는다

| 갈래 | 조건 | 처리 |
|---|---|---|
| **A. 고친다** | `failure_scenario` 가 구체적이고 확인됨 | 루프에 넣는다 |
| **B. 기각** | 오탐 / 의도된 설계 / 취향 / 시나리오가 추상적 | 고치지 않고 사유를 보고에 한 줄 |
| **C. 올린다** | 여러 파일의 구조를 바꾸는 품질 개선, 설계 층위 | 루프를 멈추지 않되 자동으로 고치지 않고 사용자에게 보고 |

`failure_scenario` 를 구체적으로 못 쓴 finding 은 A 가 될 수 없다. C 를 슬쩍 A 로 내려 조용히 고치지 않는다.

## 3. 수정 + 재확인

A 가 0 이면 재확인 생략.

1. 고친다.
2. `pnpm --filter @trade-data-manager/lab type-check && pnpm --filter @trade-data-manager/lab test`
3. 다시 병렬로:
   - lab-reviewer **재확인 모드** — 프롬프트에 그대로 넣는다:
     > 이건 재확인 패스다. 아래는 (1) 직전 발견사항 목록과 (2) 그걸 반영한 수정 diff 다. 볼 것은 두 가지뿐이다: 각 발견사항이 해소됐는지, 이 수정 과정에서 새로 생긴 문제가 있는지. 1회차에 없던 새 지적은 하지 마라. 수정 범위 밖은 보지 마라.
   - lab-verifier — **실패한 스텝만**
4. 재확인에서 나온 A 는 고치되 3회차 리뷰는 없다(테스트만 통과시키고 보고).

## 4. 조기 종료 — 상한보다 먼저

1. **같은 스텝이 같은 증상으로 2연속 FAIL** — 원인 가설이 틀렸다. 한 번 더 고치면 쓰레기만 쌓인다.
2. **원인이 코드 밖** — api 꺼짐 / 그 날짜 데이터 없음 / 시나리오가 지금 UI 와 안 맞음. 재시도 0회.
3. **고치려면 설계를 건드려야 함** — C 로 올리고 중단.

## 5. 최종 보고

```
## 검증 결과

- 게이트: type-check <상태> / test <상태>
- 리뷰: N건 → 적용 A / 기각 B / 사용자 판단 C
- 실측: <PASS 전체 | FAIL 잔존 | 미실행(사유)>

### 적용
- (파일:줄) 무엇을 왜

### 기각 (+사유)
- (파일:줄) 지적 — 사유

### 사용자 판단 필요 (C)
- 지적과, 왜 자동으로 고치지 않았는지

### 미해결 (있을 때만)
- 마지막 실패 증거 · 시도한 가설과 각각이 틀린 이유 · 넣은 수정을 남길지 되돌릴지 판단 재료
```

미해결로 끝났으면 그 사실을 첫 줄에 쓴다.
