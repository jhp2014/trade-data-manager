# 검증 루프

구현이 **끝난 뒤** 한 번 돈다. 편집 도중에 돌리지 않는다 — 반쯤 만든 코드를 리뷰하면 리뷰어가 미완성을 버그로 보고하고, 그걸 고치려다 설계가 흔들린다.

핵심 원칙 세 가지:

- **횟수가 아니라 수렴이 정지 조건이다.** 채택할 게 없으면 1회로 끝낸다. 상한은 안전망일 뿐 목표가 아니다.
- **2회차는 재리뷰가 아니라 재확인이다.** 전체를 다시 보지 않는다. 수정분 + 1회차 발견사항만 본다.
- **검증 실패는 실패로 보고한다.** PASS 위장·"아마 될 겁니다"·미검증분 끼워넣기 금지.

## 상한 요약

```
reviewer  : 1패스 + 재확인 1회   (채택 findings 0이면 재확인 생략)
verifier  : 1패스 + 재검증 2회   (FAIL 0이면 즉시 종료, 재검증은 실패 스텝만)
```

---

## 1. 사전 게이트

루프에 들어가기 전에 초록불을 확인한다. 빨간 상태로 리뷰를 돌리면 리뷰어가 이미 아는 문제를 되풀이한다.

```bash
pnpm type-check && pnpm test
```

깨져 있으면 먼저 고치고 시작한다.

## 2. code-reviewer 1패스

리뷰어는 Bash가 없다 — **무엇이 바뀌었는지는 호출자가 프롬프트에 diff로 넘긴다.** 넘기지 않으면 리뷰어가 진행을 거부한다.

```bash
git diff
```

프롬프트에 담을 것:

- **변경사항**: 위 diff 텍스트 (커밋 전이면 `git diff` + `git diff --cached`, 새 파일은 `git status`로 확인 후 전체 내용)
- **맥락**: 이 변경이 뭘 하려는 건지 한두 줄

diff가 과도하게 크면(수천 줄) 파일 전체를 통째로 넘기지 말고, 이번 작업의 **본론 파일**로 좁혀서 넘기고 나머지는 "기계적 변경"이라고 명시한다.

## 3. 발견사항 분류 — 루프에 들어가기 전 게이트

리뷰어의 findings를 **그대로 다 고치지 않는다.** 자동 반영은 구조적으로 땜빵을 양산하는 방향으로 편향된다 (리뷰어가 "null 체크 넣어라" 하면 진짜 문제가 상류 계약이어도 null 체크가 들어간다).

세 갈래로 나눈다:

| 갈래 | 조건 | 처리 |
|---|---|---|
| **A. 고친다** | `failure_scenario`가 구체적 + `verdict: CONFIRMED` | 루프에 넣는다 |
| **B. 기각한다** | 오탐 / 의도된 설계 / 스타일 취향 / `failure_scenario`가 추상적 | 고치지 않고, **기각 사유를 최종 보고에 한 줄 남긴다**. 진행은 멈추지 않는다 |
| **C. 올린다** | 설계 층위 (포트 분해, 스키마 경계, 아키텍처 변경) | **루프를 멈추고 사용자에게 보고한다.** 자동 리팩토링 금지 |

기계적 필터: **`failure_scenario`를 구체적으로 못 쓴 finding은 A가 될 수 없다.** "안전하지 않을 수 있다" 류는 B다.

C가 하나라도 있으면 A를 먼저 처리하고, 최종 보고에서 C를 별도 항목으로 올린다. C를 임의로 A로 강등해서 조용히 고치지 않는다.

## 4. 수정 라운드 + 재확인

A가 0개면 → 재확인 생략, 7번으로.

A가 있으면:

1. 수정한다.
2. `pnpm type-check && pnpm test` — 리뷰어는 실행을 못 보므로 제안이 컴파일된다는 보장이 없다. 이 게이트를 건너뛰지 않는다.
3. code-reviewer를 **재확인 모드**로 한 번 더 부른다. 프롬프트에 이 제약을 그대로 넣는다:

   > 이건 재확인 패스다. 아래는 (1) 직전 리뷰의 발견사항 목록과 (2) 그걸 반영한 수정 diff다.
   > 볼 것은 두 가지뿐이다: 각 발견사항이 실제로 해소됐는지, 그리고 **이 수정 과정에서 새로 생긴 문제**가 있는지.
   > 1회차에 지적하지 않았던 새 스타일/구조 지적은 하지 마라. 수정 범위 밖은 보지 마라.

   이 제약이 없으면 리뷰어는 diff 전체를 다시 읽고 1회차에 없던 nit을 새로 만들어낸다. LLM 리뷰어의 nit 생성은 사실상 무한하다.

4. 재확인에서 나온 A는 **고치되 3회차 리뷰는 돌리지 않는다.** 상한 도달 — 고친 뒤 type-check/test만 통과시키고 보고로 넘어간다.

## 5. browser-verifier (UI 변경일 때만)

verifier는 dev server를 띄우고 브라우저를 몰기 때문에 이 루프에서 가장 비싼 단계다. **자동으로 부르지 않는다** — 시나리오를 먼저 제시하고 사용자 승인을 받는다:

> 이 변경은 브라우저에서 관찰 가능합니다. 다음 시나리오로 실측할까요?
> 대상: <launch.json 이름>
> 1. ... 2. ... 3. ...

백엔드/타입/테스트 전용 변경이면 이 단계를 통째로 건너뛴다. 프리뷰가 증명하지 못할 변경에 서버를 띄우지 않는다.

### 시나리오는 **코드로 못 덮는 것만** 남긴다

스텝을 적기 전에 하나씩 물어라: **"이건 vitest로 덮이나?"** 덮이면 뺀다 — 브라우저로 확인하면 더 든든해 보이지만, 그 든든함의 값이 verifier 한 번 값어치는 안 된다.

남길 자격이 있는 건 셋뿐이다:

1. **실제 브라우저·서드파티가 개입하는 것** — dockview `fromJSON` 복원, `ResizeObserver` 기반 크기 측정, 캔버스 실제 페인트, lightweight-charts 시리즈 수명. jsdom이 흉내만 내고 진실을 안 말하는 자리다.
2. **손짓** — 휠·드래그·수식키 조합처럼 합성 이벤트로는 같은 코드 경로가 안 도는 입력.
3. **처음 생긴 경로의 콘솔 침묵** — "이 상태가 이 앱에 존재한 적이 없다"에 해당하는 경우(예: 열린 패널 0개). 런타임 에러 유무는 코드 읽기로 못 본다.

**스텝 3~4개가 상한이다.** 그보다 길면 덮이는 걸 안 뺐다는 뜻이니 다시 훑어라.

실측 근거(2026-08-25, 첫 실사용): 6스텝을 넣어 **182k 토큰·221툴·15분**을 썼는데, 그중 설정 영속 왕복은 슬라이스 생성자를 직접 부르는 단위 테스트가 이미 덮고 있었고 헤더 컨트롤 목록도 dom 테스트로 덮을 수 있었다. 진짜 브라우저가 필요했던 건 3개뿐이었다.

승인되면 프롬프트에 담을 것 (빠지면 verifier가 되묻는다):

- **대상**: `.claude/launch.json`의 dev server 이름, 또는 URL
- **시나리오**: "X를 클릭하면 Y가 보여야 한다" 식 구체적 스텝 목록
- **선행조건**: 특정 날짜/종목/데이터가 필요한지

### 재검증

FAIL이 있으면 수정 → `pnpm type-check && pnpm test` → verifier 재호출. **재검증 시나리오는 실패한 스텝만 넣는다.** 전체 시나리오 재실행은 비용만 2배다.

재검증은 최대 2회. 그 전에 아래 조기 종료에 먼저 걸리는 게 정상이다.

## 6. 조기 종료 — 상한보다 먼저 걸려야 하는 것들

다음 중 하나면 상한이 남아 있어도 **즉시 중단하고 사용자에게 보고한다**:

1. **같은 스텝이 같은 증상으로 2연속 FAIL** — 원인 가설이 틀렸다는 뜻이다. 틀린 가설로 한 번 더 고치면 코드에 쓰레기만 쌓인다.
2. **원인이 코드 밖** — 선행 데이터 없음 / 시나리오 스텝이 현재 UI와 안 맞음 / dev server가 안 뜸. 재시도 **0회**. 이건 수정 대상이 아니라 입력 오류다.
3. **고치려면 설계를 건드려야 함** — C로 승격, 중단.

## 7. 최종 보고

루프가 어떻게 끝났든 아래를 남긴다. 특히 **상한 도달로 끝났을 때** 이 보고가 사용자가 이어받는 유일한 재료다.

```
## 검증 루프 결과

- 리뷰: N건 발견 → 적용 A건 / 기각 B건 / 상신 C건
- 실측: <PASS 전체 통과 | FAIL 잔존 | 미실행(사유)>
- 게이트: type-check <상태> / test <상태>

### 적용
- (파일:줄) 무엇을 왜 고쳤는지

### 기각 (+사유)
- (파일:줄) 지적 내용 — 기각 사유

### 사용자 판단 필요 (C)
- 설계 층위 지적과, 왜 자동으로 고치지 않았는지

### 미해결 (상한 도달 시에만)
- 마지막 실패 증거 (콘솔/네트워크/스크린샷 관찰)
- **시도한 원인 가설과 각각이 왜 틀렸는지**
- 그동안 넣은 수정이 독립적으로 의미 있는지 (되돌릴지 남길지 판단 재료)
```

미해결로 끝났으면 그 사실을 문장 첫 줄에 쓴다. 적용한 것들을 먼저 나열해서 성공처럼 보이게 만들지 않는다.
