# 설계 결정 로그 관리

`.claude/decisions.md`는 `architecture-map.md`("어디가 책임")의 짝 — "왜 이렇게 정했고 뭘 기각했는지"를 **현재 상태만** 담는다. 이력이 아니다: 결정이 뒤집히면 그 항목을 새 내용으로 **덮어쓴다**. `planner`·`code-reviewer` 서브에이전트가 이 파일을 읽으므로, 여기 적은 것의 품질이 걔들 판단력에 그대로 반영된다.

## 언제 적는가 (판단 기준)

적을 만한 것 — **하나라도 해당하면 후보**:
- 여러 파일/레이어에 걸친 규칙이 새로 생겼다(한 파일 주석으로는 안 보이는 것).
- 검토했다가 **기각한 대안**이 있다(코드에 흔적이 안 남아 나중에 같은 논의가 반복될 위험).
- 기존 decisions.md 항목이 이번 결정으로 뒤집혔다.

적지 않는 것:
- 한 파일 안에서 끝나는 이유(그 파일 주석이면 충분).
- 아직 확정 안 된 논의 중인 안(결론 나면 그때).
- 코드만 봐도 뻔한 것.

애매하면 억지로 적지 않는다 — "여기가 두꺼워지면 이미 실패한 것"이 파일 자체의 원칙이다.

## 절차

1. **자율 트리거 시**: 방금 결론 난 결정이 위 기준에 해당하는지 스스로 판단한다. 애매하면 사용자에게 "이거 결정로그에 남길까요?" 물어본다 — 억지로 판단하지 않는다.
2. `.claude/decisions.md`를 읽는다. 관련 섹션이 있는지, **기존에 겹치는 항목이 있는지** 확인한다(있으면 덮어쓸 대상 — grep 으로 관련 키워드 검색).
3. 항목을 쓴다. 형식은 기존 항목들과 맞춘다:
   - **굵게 한 줄 규칙** — 무엇이 참인지, 명령형으로.
   - 필요하면 왜(한두 문장), 여러 레이어에 걸치면 어느 레이어들인지.
   - 기각된 대안이 있으면 한 줄로.
   - 커밋 해시·관련 메모리(`[[name]]`) 링크 — 전체 논의는 거기 있다는 걸 명시. **여기서 논의 전체를 재현하지 않는다.**
4. 이 결정이 "어디가 책임인지"도 바꿨다면(단순히 왜가 아니라 구조 자체가 이동했다면) `.claude/architecture-map.md`도 같이 갱신해야 하는지 확인한다 — 잊기 쉬운 지점.
5. Edit 로 반영한다. 자율 트리거로 왔다면(사용자가 직접 요청한 게 아니라면) 뭘 적었는지 한두 줄로 알려서 사용자가 바로 고칠 기회를 준다 — 조용히 넘어가지 않는다.

## 메모리와의 경계

- **decisions.md**: "코드를 지금 어떻게 짜야 하는가"를 지배하는 것. `planner`/`code-reviewer`도 읽는다.
- **개인 메모리**(`type: project`/`feedback`): 논의 경위·사용자와의 합의 과정·세션 상태. 서브에이전트는 안 읽는다.

결정을 적을 때 "왜 이렇게 됐는지"의 전체 서사는 보통 이미 메모리에 있다(이 대화 자체가 project 메모리로 남을 것이므로) — decisions.md 항목에서 그 메모리를 링크만 하고, 서사를 복붙하지 않는다.
